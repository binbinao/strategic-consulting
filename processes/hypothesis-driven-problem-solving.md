# 假设驱动问题解决

> 在深入分析之前先形成假设，再用数据/事实去证伪或证实，从而加速收敛到答案的咨询工作流。

## 起源与定位

假设驱动问题解决（Hypothesis-Driven Problem Solving / 假设驱动）是 MBB 等顶级咨询公司的标志性工作流 [需核实]。该方法在 1980s 随着咨询行业项目周期压缩而被系统化推广，业内常将其与 MECE 议题树绑定使用 [需核实]。无单一正式出版物作为起源——它是咨询团队在工作实践中演化出的方法论。

## 核心内容

核心循环：

1. **假设（hypothesis）先行**——基于经验和初步事实形成对核心问题的可能答案
2. **拆解**——把假设拆为多个可被独立证伪的子命题
3. **杀手实验（killer experiment）设计**——识别能最快判定假设真假的关键数据点
4. **数据收集**——优先回答"能否证伪"，而非追求完整图景
5. **修正与再假设**——若被证伪，重设假设；若证实，加固证据

与科学方法的关系：本质上是 Popper 式的"可证伪性"在商业问题上的应用——不要试图"证实"假设，而要试图"推翻"它。

## 适用与不适用

**适用**：

- 时间紧、有清晰业务问题的咨询项目
- 需要快速收敛的董事会决策
- Case interview 中的问题分析

**不适用**：

- 问题本身未被定义的探索性研究
- 数据稀缺的全新领域（无足够证据形成合理假设）
- 需要"无框架观察"的开放式田野研究
- 高度合规/法务场景（结论先行不合规惯例）

## 局限与争议

- 假设先行引入分析师的先验偏差——若初始假设方向错了，可能错过正确方向
- 需要分析师有较强的先验判断力，对新手不友好
- 客户文化若偏好"先看数据"则冲突大
- [争议] 假设驱动 vs. 数据驱动：学术界倾向后者的严谨性，咨询业倾向前者的速度
- [争议] 假设的"可证伪性"在商业问题中往往难严格定义——很多时候只能"修正"而非"证伪"

## 与其他方法论的关系

- **前置**：MECE 议题树提供假设所挂载的"问题骨架"，二者几乎总是组合使用
- **配套**：明托金字塔原理把检验后的结论包装为自上而下的沟通结构
- **思维训练**：与"第一性原理"、"5 Why"等方法有相通之处——都强调"快速形成方向"
- **批评替代**：纯归纳式数据分析（data-first）与之对立，强调"让数据说话"

假设驱动是我 MBA 之后第一个重新塑造我工作方式的咨询方法——也是我后来发现被误用最多的。

**经验层**：我做过十几次假设驱动项目。最有效的几次都满足一个模式：客户给了一个有时间压力的"必须出结论"的命题（董事会决策窗口 / 并购紧迫期）。在压力下，假设驱动流程强迫分析师先收敛到"我猜答案是什么"，再用数据去验。这种"先答案后数据"的顺序在压力下反而有效，因为开放搜索在时间紧的项目里是灾难——分析师会陷入数据收集而不出结论。最糟的是几次"假设对了但客户文化不接"——客户内部文化是"先看数据再下结论"的，麦肯锡式的"先猜后验"会被客户解读为"你们已经决定了，现在来找数据支持"。

**判断层**：我现在倾向在"问题已定义清楚"的项目里用假设驱动——商业模式诊断、行业并购评估、明确的运营改进项目。这类项目里"答案的可能形态有限"，先收敛到几个假设比开放探索高效。但在"问题本身未被定义清楚"的项目里——例如 CEO 说"我们公司哪里出了问题"——假设驱动是危险的，因为分析师的先验假设会过早收敛。我倾向把这种"开放式问题"的项目与"封闭式问题"的项目区分开：前者用 MECE + 议题树做开放探索，后者用假设驱动 + 杀手实验做定向验证。

**反思层**：我对假设驱动最大的保留意见是"假设的来源"。框架假设分析师有合理的"初始假设"，但对新手分析师来说，"先猜"是从哪里来的？是上一份报告的延伸？导师的传授？还是客户告诉你的？如果初始假设不是分析师自己的判断，框架就成了"形式上看起来像科学、实际上在传递别人的偏见"。我见过最严重的案例：一个分析师用了"客户 CEO 的直觉判断"作为初始假设，然后用两周数据收集去"验证"，最终报告只是把 CEO 的话换成了数据——这违背了假设驱动"可证伪性"的核心。

**关联层**：假设驱动与其他工具的搭配——
- 与 `mece` 是必备组合（MECE 给假设挂载的"问题骨架"）
- 与"演绎 vs 归纳"哲学配对——假设驱动偏演绎（从结论推数据），data-first 偏归纳（从数据归纳结论）
- 与 Popper 的科学哲学直接连接——Karl Popper 1934 年的 *The Logic of Scientific Discovery* 是假设驱动的思想源头
- 与 case interview 训练几乎是同义——咨询面试的本质就是"先假设后验"

**应用偏好**：我用假设驱动的场景：
- 时间紧迫且问题定义清晰的项目
- 并购紧迫期（"必须 6 周内出结论"）
- 董事会决策窗口（"下次董事会需要给建议"）

我不用假设驱动的场景：
- 问题未被定义清楚的开放式咨询
- 数据稀缺的全新领域（假设基础不足）
- 客户文化偏好"先看数据"——这种客户用 MECE 议题树 + 假设驱动的组合容易引起反弹
